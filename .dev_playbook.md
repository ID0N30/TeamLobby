# 📘 Playbook de Desarrollo: Estándar React + Firebase + Next.js + Vercel

Este documento recopila las mejores prácticas, arquitecturas probadas, soluciones a errores recurrentes y la guía paso a paso para iniciar, desarrollar y desplegar proyectos web con la pila **React / Next.js + Firebase (Auth/Firestore) + Vercel**.

---

## 🛠️ PARTE 1: ESTÁNDAR GLOBAL DE DESARROLLO

### 1. 🚀 Configuración Inicial del Proyecto (Setup Standard)
- **Framework**: Next.js (App Router) + TypeScript + Tailwind CSS.
- **Variables de Entorno**:
  - Crear `.env.local` para desarrollo local y configurarlo en Vercel Dashboard para producción.
  - Soporte para **Firebase Local Emulator Suite**:
    ```env
    NEXT_PUBLIC_USE_EMULATOR=true
    ```
- **Inicialización de Firebase (`src/lib/firebase.ts`)**:
  - Evitar inicializaciones duplicadas revisando `getApps().length`.
  - Conectar a emuladores locales en entorno de desarrollo cuando `NEXT_PUBLIC_USE_EMULATOR === 'true'`:
    ```typescript
    if (process.env.NEXT_PUBLIC_USE_EMULATOR === 'true') {
      connectFirestoreEmulator(db, '127.0.0.1', 8080);
      connectAuthEmulator(auth, 'http://127.0.0.1:9099');
    }
    ```

---

### 2. ⚡ Arquitectura de Estado y Sincronización en Tiempo Real (Real-Time State Pattern)
- **Zustand + Firestore (`onSnapshot`)**:
  - El store de Zustand gestiona el estado reactivo de la UI de forma fluida.
  - La sincronización en tiempo real se suscribe mediante `onSnapshot` en la página principal (`/room/[id]`) y actualiza el store con `useStore.setState({...})`.
  - **Patrón Antibucle Infinito**:
    - Usar una referencia `lastRemoteSnapshot = useRef("")` para almacenar la versión JSON de los datos remotos.
    - Antes de llamar a `savePlayerInRoom` en un `useEffect`, comparar los datos locales con `lastRemoteSnapshot` para asegurar que solo las mutaciones locales del usuario disparen una escritura remota.

---

### 3. 🛡️ Protección de Cuota de Firebase (Quota Protection & Offline Fallback)
- **Rate Limiting de Escrituras (`isWriteRateLimited`)**:
  - Mantener un registro de marca de tiempo (`lastWriteTimeMap`) por documento.
  - Establecer un intervalo mínimo de escritura (ej. 1.5 segundos por documento) para evitar ráfagas descontroladas o bucles infinitos.
- **Respaldo Local Offline (`localStorage`)**:
  - Ante fallos de red o errores de cuota (`resource-exhausted`), guardar automáticamente el estado crítico en `localStorage` (`dnd_offline_char_[id]`).
- **Manejo de Errores Silenciosos con Fallbacks**:
  - Envolver todas las operaciones `setDoc`, `updateDoc`, `deleteDoc`, `addDoc` en bloques `try/catch` para que un fallo de red o cuota no rompa la aplicación.

---

### 4. 📜 Sistema Global de Logs de Errores (`errorLogger`)
- **Captura Centralizada (`src/lib/errorLogger.ts`)**:
  - Escuchadores de ventana globales (`window.onerror` y `unhandledrejection`).
  - Almacenamiento de los últimos 100 errores en `localStorage` (`dnd_system_error_logs`).
- **UI Notificadora (`ErrorToast.tsx`)**:
  - Notificación tipo flotante cuando ocurre un error crítico o de cuota.
  - Modal Inspector para visualizar logs, filtrar por severidad y copiar reportes al portapapeles.

---

### 5. 🚢 Despliegue en Vercel (Checklist de Producción)
1. **Verificación Previa**: Ejecutar siempre `npm run build` en local antes de subir cambios. Debe compilar con 0 errores de TypeScript y Next.js.
2. **Variables de Entorno en Vercel**:
   - `NEXT_PUBLIC_FIREBASE_API_KEY`, `NEXT_PUBLIC_FIREBASE_PROJECT_ID`, etc.
   - Asegurarse de mantener `NEXT_PUBLIC_USE_EMULATOR=false` (o no definirlo) en producción.
3. **Reglas de Seguridad Firestore (`firestore.rules`)**:
   - Configurar reglas adecuadas en la consola de Firebase antes del lanzamiento.

## 🗂️ PARTE 2: REGISTRO DE PROYECTOS Y LECCIONES APRENDIDAS

### 🏰 Proyecto 1: Dungeon & Dragons Companion (`dnd-companion`)
- **Stack**: Next.js 16 (App Router), Tailwind CSS, Zustand, Firebase Auth + Firestore, Lucide Icons, Framer Motion.
- **Lecciones Clave y Errores Resueltos**:

#### 🔴 Error 1: Cuota Excedida de Firestore (`resource-exhausted`) y Cierre de Sesión
- **Causa**: Un `useEffect` de auto-guardado en el cliente disparaba `savePlayerInRoom` en cada render sin validar si los datos venían del servidor o eran cambios locales, generando un bucle infinito de escrituras.
- **Solución**:
  1. Implementación de `lastRemoteSnapshot` con `useRef` para evitar escrituras en eco.
  2. Implementación de limitador de tasa de 1.5s (`isWriteRateLimited`) en `src/lib/rooms.ts`.
  3. Integración del Firebase Local Emulator Suite para desarrollo local libre de límites de cuota.

#### 🔴 Error 2: Registro de Acciones (Logs) No Sincronizado en Tiempo Real
- **Causa**: `addLog` en el store Zustand solo modificaba el array local `logs`. Al recibir instantáneas de Firestore, el array se sobrescribía.
- **Solución**:
  - Se actualizó `addLog` en `src/store/useStore.ts` para invocar `addRoomLog(roomId, message)`, guardando cada acción en la subcolección `rooms/[roomId]/logs` de Firestore y transmitiéndola a todos los jugadores mediante `subscribeRoomLogs`.

#### 🔴 Error 3: El Modo Combate No se Activaba en las Pantallas de los Jugadores
- **Causa**: `toggleCombatMode` cambiaba el estado en el store Zustand del DM, pero no enviaba `isCombatMode: true` ni la orden de iniciativa al documento de la sala en Firestore (`rooms/[roomId]`). Por ello, la suscripción en tiempo real del jugador sobrescribía el estado a `false`.
- **Solución**:
  - Se modificó `toggleCombatMode` y `advanceTurn` en `src/store/useStore.ts` para invocar `updateRoomState` y `savePlayerInRoom`, propagando el estado de combate a la base de datos y notificando en tiempo real a la interfaz de todos los jugadores.

#### 🔒 Privacidad Estricta de Datos del Jugador vs DM (Notas Personales Privadas)
- **Desafío**: Se requería una pestaña de "Notas" para que cada jugador pudiera escribir anotaciones personales, títulos y secretos que **NO deben ser visibles por el DM**.
- **Solución**:
  - Se implementó el almacenamiento de las notas exclusivamente en el `localStorage` local del navegador del cliente (`dnd_private_notes_[character.id]`). Al no enviarse al estado del personaje en Firestore (`savePlayerInRoom`), los datos nunca viajan por red ni pueden ser inspeccionados por el DM.
  - Se añadió la UI de creación, edición y eliminación de notas con avisos explícitos de privacidad (`🔒 100% Privado`).

#### 🌟 Ascenso Celestial de Nivel y Notificación Sincronizada
- **Desafío**: Implementar la funcionalidad para que el DM suba de nivel a un jugador o a la party entera con confirmación previa, aplicando cálculos automáticos de D&D 5e (HP Máximo, Bonificador de Competencia, Espacios de Hechizo, Rasgos de Clase) y notificando a los jugadores con una alerta victoriosa celestial sin emojis.
- **Solución**:
  - Se añadieron los métodos `levelUpPlayer` y `levelUpParty` en el store Zustand sincronizados con Firestore (`updateRoomState` + `savePlayerInRoom`).
  - Se creó el componente `CelestialLevelUpModal.tsx` con ráfaga de partículas doradas/azules, resplandores celestiales, 0 emojis y resumen automático de mejoras D&D 5e con indicaciones del DM.

### 🎮 Proyecto 2: TeamLobby (`teamlobby`)
- **Stack**: Vite + React 18, React Router v6, Tailwind CSS, Firebase Realtime Database + Firebase Auth (Google + Invitados efímeros), Google GenAI SDK (`gemini-3-flash-preview`), Lucide Icons, Vercel (Deploy SPA).
- **Descripción**: Galería colaborativa de videojuegos por salas en tiempo real donde comunidades o grupos de amigos postulan juegos, votan por ellos, filtran por plataformas, chatean, resuelven qué jugar mediante Ruleta/Votación ("Ready Command") y reciben recomendaciones inteligentes de IA.
- **Lecciones Clave y Errores Resueltos**:

#### 🔴 Desafío 1: Estructura de Mapas vs Arrays en Firebase Realtime Database
- **Causa**: A diferencia de bases de datos relacionales o arrays estándar de JavaScript, Firebase Realtime Database almacena arrays dispersos y subcolecciones (`votedBy`, `comments`, `members`, `chatHistory`) como objetos con claves únicas (`Record<string, T>`). Al recuperar los datos en el cliente, tratar un mapa como un array provocaba errores de ejecución (`.map is not a function` o fallos en spreads).
- **Solución**:
  1. En `types.ts`, se tiparon las colecciones como `Record<string, Comment>` y `Record<string, boolean>`.
  2. En `roomService.ts`, se implementó la utilidad `parseCollection(obj)` dentro de `subscribeToRoom`, garantizando que cualquier objeto/mapa recibido sea convertido a array plano filtrando elementos vacíos antes de propagarlo a los componentes de la interfaz.

#### 🖼️ Desafío 2: Almacenamiento de Portadas sin Firebase Storage (Compresión Client-Side)
- **Desafío**: Permitir que los usuarios suban carátulas personalizadas para juegos propuestos sin sobrepasar los límites de cuota de la base de datos y sin incurrir en costes de Firebase Storage.
- **Solución**:
  - Se diseñó `uploadGameImage` en `services/firebaseService.ts` usando un `<canvas>` en el navegador que redimensiona automáticamente la imagen a un máximo de 800x600 manteniendo la relación de aspecto y la exporta en JPEG al 70% de calidad.
  - Esto comprime archivos de más de 2MB a strings Base64 de entre 50KB y 80KB, permitiendo su persistencia directa y ultrarrápida dentro del payload del juego en Realtime Database.

#### 👥 Desafío 3: Gestión Híbrida de Sesiones (Google Auth + Invitados Efímeros con Limpieza)
- **Desafío**: Reducir la fricción para amigos que se unen a una partida rápida sin obligarlos a autenticarse con Google, pero sin saturar la base de datos de usuarios fantasmas.
- **Solución**:
  1. Sistema dual de autenticación en `authService.ts` y `App.tsx`: cuentas verificadas con Google Auth y sesiones temporales de invitado almacenadas en `sessionStorage` (`guestId`, `guestAlias`) con avatares automáticos de DiceBear Bottts.
  2. Conteo dinámico de invitados activos en salas para asignarles nombres ordenados (`Invitado 1`, `Invitado 2`).
  3. Script de backend administrativo en `functions/cleanup-guests.cjs` con `firebase-admin` para depurar periódicamente nodos huérfanos de invitados en `users` y `userSummaries`.

#### 🎲 Desafío 4: Dinámica "Ready Command" (Ruleta Aleatoria vs Votación Democrática)
- **Desafío**: Resolver la indecisión del grupo para elegir qué jugar mediante un flujo sincronizado en tiempo real que recolecte sugerencias de los jugadores presentes, valide un mínimo de candidatos y elija al ganador de manera justa.
- **Solución**:
  - Creación del nodo `readySession` en la sala con estados controlados (`idle` -> `collecting` -> `results`).
  - Sincronización del estado de jugador listo (`isReady`) con su propuesta de juego (`suggestions`).
  - Dos modalidades de resolución:
    - **Ruleta**: Selección aleatoria animada con retardo de 3 segundos para suspense.
    - **Votación**: Conteo ponderado de votos por juego con resolución y soporte para desempates o "empates técnicos" múltiples.

#### 🚀 Desafío 5: Evolución de Catálogo y Reemplazo de IA por Autocompletado de Steam
- **Desafío**: La recomendación con IA por API Key generaba costos, latencia y dependencias externas. Asimismo, mantener una biblioteca global en RTDB (`/library`) provocaba suscripciones WebSocket pesadas e innecesarias para cada miembro de la sala.
- **Solución**:
  - Se eliminó el SDK de Gemini AI y el nodo `/library`.
  - Se implementó en `services/gameSearchService.ts` un sistema de autocompletado híbrido: un catálogo curado local de más de 50 juegos populares (0ms latencia) y búsqueda en vivo contra la API de Steam Store mediante proxy `/api/steam-search`. Al seleccionar una sugerencia, se autocompletan instantáneamente carátula en alta definición, plataformas, género y enlace de tienda.
  - Al ingresar un juego en una sala, se aprueba de forma directa e independiente, eliminando burocracia de moderación y ahorrando miles de lecturas/escrituras en Firebase RTDB.

#### 🔊 Desafío 6: Feedback Acústico No Invasivo (Web Audio API Sintetizado)
- **Desafío**: Proporcionar respuesta auditiva agradable e inmersiva al interactuar con la app (votar, ruleta, autocompletado, chat) sin cargar archivos `.mp3` pesados por red ni resultar molesto.
- **Solución**:
  - Se desarrolló `services/soundService.ts` usando Web Audio API puro (osciladores sintetizados analógicos `sine` y `triangle` con control estricto de ganancia y volumen moderado del 10-12%).
  - Soporte global de silenciado (Mute/Unmute) persistido en `localStorage` (`teamlobby_sound_muted`).

#### 📦 Desafío 7: Optimización de Bundling y Seguridad en Producción (Vite + Vercel)
- **Desafío**: Prevenir chunks monolíticos pesados de JavaScript y configurar de forma segura el proxy y políticas de CSP para Steam en Vercel.
- **Solución**:
  - En `vite.config.ts`, se implementó `manualChunks` dividiendo el bundle en `vendor-react`, `vendor-firebase` y `vendor-icons`, reduciendo el chunk principal a solo ~107 kB.
  - En `vercel.json`, configuración de rewrite para `/api/steam-search` y autorización de CDNs de Steam (`*.steamstatic.com`, etc.) en Content-Security-Policy.

#### 🚪 Desafío 8: Flujo de Acceso Fricción Cero (Invitado por Defecto + Login Modal Contextual)
- **Desafío**: Bloquear la aplicación o las salas con una pantalla de login externa o muro de autenticación disuade a amigos que se unen rápidamente mediante un link compartido para ver una sala o votar.
- **Solución**:
  - Se eliminó la pantalla fija de login. Si no hay sesión activa de Google, la aplicación inicializa automáticamente un usuario en modo invitado (`createGuestUser`).
  - Todas las salas y la página principal son explorables de inmediato.
  - La autenticación se transformó en un modal/alerta interactivo (`LoginModal` con hook `useAuthModal`) que puede ser invocado voluntariamente (botones visibles en header y barra lateral) o según sea necesario (al intentar proponer un juego o comentar).
  - Al completar la autenticación con Google en caliente, el usuario actualiza su sesión en tiempo real sin recargar ni abandonar la sala.

#### 🟢 Desafío 9: Presencia en Tiempo Real, Invitados Efímeros y Depuración de la Escuadra (Squad Members)
- **Desafío**: Si un invitado cerraba el navegador o la pestaña, su nodo quedaba huérfano en `rooms/${code}/members`, saturando la lista de "Squad Members" y bloqueando la función de "READY" al figurar como participantes desconectados que nunca se ponían listos.
- **Solución**:
  - Se implementó presencia en tiempo real con Firebase RTDB (`.info/connected`).
  - **Invitados (`isGuest: true`)**: Al conectarse, se programa `onDisconnect().remove()` en su miembro, sugerencias y votos. Si pierden la conexión, cierran la pestaña o pulsan *LEAVE*, el servidor los elimina de inmediato. Además, la interfaz filtra `members` para que los invitados aparezcan **única y exclusivamente si están online**.
  - **Cuentas Registradas (`!isGuest`)**: Al desconectarse, se programa `onDisconnect().update({ isOnline: false, isReady: false })`. Permanecen en la sala como miembros de la comunidad pero con indicador visual `OFFLINE`, avatar atenuado y estado no listo.
  - **Sincronización de READY**: Se vinculó el botón READY con el estado real del usuario en la sala (`currentUserMember?.isReady`) para un feedback sonoro y visual exacto.
  - **Regla de Hooks en React**: Mantener siempre todos los hooks (`useMemo`, `useEffect`) **antes** de cualquier retorno temprano (`if (!room) return <Loader />`) para evitar el error de *"Rendered more hooks than during the previous render"*.
